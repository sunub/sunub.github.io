# 0002: 반응형 스타일링 아키텍처 및 SSOT 설계 원칙

상태: accepted

**맥락 (Context):**
블로그 인프라를 Vercel 기반의 정적 렌더링(Static) 아키텍처로 이전함에 따라, 뷰(View) 영역 또한 예측 가능하고 강력하게 통제된 아키텍처가 필요해졌습니다. 기존 코드베이스는 `clamp` (Viewport 너비 기반), `cqw` (Container 너비 기반), 그리고 하드코딩된 Magic Number가 목적 없이 혼재되어 있었으며, 렌더링과 반응형 단위에 대한 단일 진실 공급원(SSOT, Single Source of Truth)이 부재했습니다.

**결정 (Decision):**
성능 최적화와 유지보수성 향상을 위해 프론트엔드 반응형 레이아웃 및 디자인 토큰 관리에 대해 다음과 같은 핵심 원칙을 채택합니다.

1. **레이아웃 매커니즘 분리**: 
   - 매크로 레이아웃(페이지 전체 프레임, 뷰포트 기준)은 `@media` 쿼리를 사용합니다.
   - 마이크로 레이아웃(독립적이고 재사용 가능한 컴포넌트 내부 배치)은 `@container` 쿼리를 사용합니다.
   - 글로벌 `#next` 래퍼에 무분별하게 선언된 `container: root`는 지양하고 목적에 맞게 분리합니다.
2. **Native CSS 변수 기반 SSOT**: 
   - `styled-components`의 무거운 런타임 `ThemeProvider` 객체를 사용하지 않습니다. 
   - 대신 렌더링 성능과 하드웨어 가속의 이점을 극대화하기 위해 `globals.css`의 `:root` 네이티브 CSS 변수(`var()`)를 스타일링의 단일 진실 공급원(SSOT)으로 사용합니다.
3. **디자인 토큰 3단계 계층화 및 캡슐화**: 
   - 코드베이스 전반에서 Magic Number 하드코딩을 엄격히 금지합니다.
   - 모든 반응형 수치는 3단계 계층(Global Tokens -> Semantic Tokens -> Component Tokens)으로 명명하여 관리합니다.
   - 이 토큰 규칙은 CSS 레벨에서 통제하는 것이 아니라, 디자인 시스템 개념이 적용된 캡슐화된 React Component API를 통해서만 강제됩니다.

**왜 이 결정을 내렸는가 (Why):**
`ThemeProvider`와 같은 JS 객체 기반 테마는 다크 모드 전환이나 뷰포트 변경 시 전체 React 트리의 연쇄적인 리렌더링과 런타임 CSS 재계산을 유발하여 막대한 성능 오버헤드를 발생시킵니다. 네이티브 CSS 변수를 활용하면 이 오버헤드를 제로(0)에 가깝게 만들 수 있습니다. 
또한 개발자의 자유도를 제한하고 엄격한 토큰 계층과 컴포넌트 캡슐화를 도입해야만, 장기적인 유지보수성과 예측 가능한 크로스 브라우저 렌더링을 담보할 수 있기 때문입니다.

**결과 (Consequences):**
- 모든 반응형 컴포넌트 설계 시 자신이 어떤 레이아웃 컨텍스트(`@media` vs `@container`)에 속하는지 명확히 하고 단위를 결정해야 합니다.
- 새로운 스타일 수치(간격, 크기 등)가 필요할 경우 반드시 `globals.css`의 토큰 계층 구조에 맞추어 변수를 먼저 정의해야 합니다.
- 개발자는 개별 페이지에서 컴포넌트의 CSS(예: padding, margin)를 직접 덮어씌워 수정하는 대신, 캡슐화된 컴포넌트를 그대로 사용하고 오직 정해진 Props를 통해서만 제어해야 합니다.
