# ADR-0001: 개인 블로그 운영 구조를 EC2 런타임에서 Vercel 기반 정적 배포로 이전한다

- Status: Proposed
- Date: 2026-03-24

## 배경

현재 블로그는 `frontend + backend` 모노레포로 구성되어 있다.

- `frontend`는 Next.js App Router 기반으로 동작한다.
- `backend`는 Nest 기반 API 서버로 동작한다.
- GitHub Actions는 빌드 후 AWS SSM을 통해 EC2 인스턴스에서 배포 스크립트를 실행한다.
- 프런트는 `next.config.ts`의 `rewrites()`를 통해 `/posts/*`, `/api/*` 요청을 백엔드로 전달한다.

이 구조는 SSR, 백엔드 API, CI/CD, AWS 배포 자동화까지 포함한 전체적인 서비스 운영 흐름을 경험해보기 위해 선택한 구조였다. 학습 목적과 포트폴리오 관점에서는 충분히 의미가 있었다.

하지만 현재 시점에서 블로그의 실제 제품 성격과 운영 비용을 다시 평가해보면, 이 구조는 개인 블로그 운영 목적에 비해 과한 부분이 분명하다.

## 현재 구조 요약

현재 백엔드의 핵심 역할은 다음에 가깝다.

- `posts/` 폴더의 `md/mdx` 파일을 읽어 인덱스를 생성한다.
- 최신 글, 범위별 글, 카테고리별 글, 아카이브 요약 데이터를 반환한다.
- 본문 검색 API를 제공한다.

즉, 데이터베이스에 저장된 사용자 데이터나 실시간 비즈니스 상태를 다루는 서버라기보다, 파일 기반 콘텐츠를 읽어 정리하고 조회용 API로 노출하는 서버에 가깝다.

반면 프런트엔드 쪽에는 이미 로컬 파일과 `posts.jsonl`을 직접 읽는 로직이 일부 존재한다. 이는 현재 구조가 이미 완전한 서버 중심 구조라기보다, 정적 생성과 런타임 API가 혼합된 과도기 상태임을 보여준다.

## 비용 측면의 문제

### 1. 고정비 비중이 지나치게 높다

개인 블로그의 트래픽은 일반적으로 크지 않다. 이 경우 비용의 중심은 전송량이나 요청 수 같은 변동비보다 다음과 같은 고정비에 놓이게 된다.

- EC2 인스턴스 비용
- Public IPv4 비용
- EBS 비용

이 비용들은 방문자가 많지 않아도 계속 발생한다. 즉, 블로그의 실제 사용량과 무관하게 서버를 켜 두는 것 자체가 비용의 중심이 된다.

### 2. 캐시 최적화만으로는 핵심 비용이 줄지 않는다

Cloudflare나 CDN 계층은 다음에 효과적이다.

- 정적 자산 캐시
- TLS 종료
- 전송 최적화
- 원본 서버 보호

하지만 EC2가 계속 살아 있어야 하는 구조라면, 캐시 효율을 높여도 다음 비용은 그대로 남는다.

- EC2 상시 운영 비용
- Public IPv4 비용
- EBS 비용

즉, 현재 구조의 비용 문제는 "캐시를 더 잘 태우면 해결되는 문제"가 아니라 "서버를 계속 유지해야 하는 구조"에서 발생하는 문제다.

### 3. 운영 부담도 비용이다

직접 청구서에 보이지 않더라도 다음 항목들은 모두 운영 비용으로 간주해야 한다.

- EC2 인스턴스 관리
- 배포 실패 대응
- `nginx` 또는 리버스 프록시 설정 유지
- 보안 패치
- 인스턴스 상태 점검
- SSM 기반 배포 스크립트 관리

이 부담은 개인 블로그처럼 도메인이 단순한 서비스에서는 기능 가치보다 유지 비용이 더 커지기 쉽다.

## 현재 구조가 제품 성격 대비 과한 이유

### 1. 콘텐츠의 본질이 정적이다

이 블로그의 원천 데이터는 `posts/` 폴더에 존재하는 `md/mdx` 파일이다.

- 게시글은 파일 기반으로 관리된다.
- 사용자별 실시간 데이터가 핵심 도메인이 아니다.
- 트랜잭션성 데이터 저장소가 필요하지 않다.
- 대규모 검색 인프라가 필요할 정도의 데이터 규모가 아니다.

현재 글 수와 데이터 크기를 고려하면, 검색과 아카이브도 빌드 산출물 기반으로 충분히 다룰 수 있다.

### 2. 코드 자체도 이미 정적 생성 방향에 가깝다

현재 포스트 페이지는 이미 정적 생성에 가까운 구조를 일부 사용 중이다.

- 카테고리 및 글 상세 경로에 `generateStaticParams()`가 있다.
- 포스트 상세 페이지에는 `revalidate` 설정이 들어가 있다.

즉, 코드베이스 자체가 상시 살아 있는 런타임 서버보다 "빌드 시 생성 + 필요 시 재배포" 패턴에 더 잘 맞는 방향을 이미 갖고 있다.

### 3. 서버가 꼭 필요한 기능이 아니라, 구현 방식 때문에 남아 있는 기능이 있다

현재 런타임 서버를 유지하게 만드는 대표 기능은 다음과 같다.

- 아카이브 summary/range API
- 최신 글 range API
- 검색 API
- 프런트의 rewrite 경유 요청

하지만 이 기능들은 사용자 인증, 결제, 세션, 멀티테넌시, 실시간 상태 동기화처럼 서버 상주가 꼭 필요한 기능이 아니다. 대부분은 빌드 시 생성한 JSON 산출물과 클라이언트 로직으로 대체 가능하다.

### 4. 동일한 도메인을 두 군데에서 다루고 있다

현재 프로젝트는 블로그 콘텐츠를 다루는 책임이 프런트와 백엔드에 나뉘어 있다.

- 백엔드는 파일 기반 인덱싱과 API 응답을 담당한다.
- 프런트도 일부는 로컬 파일과 인덱스를 직접 읽는다.

이 구조는 학습용으로는 의미가 있었지만, 운영 관점에서는 책임이 분산되어 있고 중복된 복잡도를 만든다.

## 왜 이전을 결정하는가

이전 결정의 핵심 이유는 다음과 같다.

### 1. 비용 구조를 제품 성격에 맞추기 위해

개인 블로그는 상시 서버 런타임보다 정적 배포가 훨씬 자연스럽다. 현재 비용 구조의 핵심 부담은 트래픽이 아니라 서버 고정비이며, 이를 줄이려면 서버를 더 효율적으로 쓰는 것보다 서버 자체를 제거하는 편이 효과적이다.

### 2. 운영 복잡도를 줄이기 위해

현재 구조는 학습 관점에서는 많은 경험을 제공했지만, 운영되는 블로그의 관점에서는 불필요한 이동 부품이 많다. 구조를 단순화하면 배포, 장애 대응, 설정 관리, 비용 추적이 모두 쉬워진다.

### 3. 아키텍처를 콘텐츠 도메인에 맞추기 위해

현재 블로그는 "실시간 서비스"보다 "정적 콘텐츠 사이트"에 가깝다. 따라서 운영 구조도 그 성격에 맞춰 정적 생성 중심으로 재편하는 것이 더 합리적이다.

### 4. 학습 경험은 보존하되, 운영 구조는 현재 목적에 맞게 바꾸기 위해

EC2, Nest, SSM, rewrite 기반 운영 구조를 직접 경험한 사실 자체는 충분히 가치 있다. 다만 그 경험을 보존하는 최선의 방법은 더 이상 쓰지 않는 구조를 메인 운영 경로에 남겨 두는 것이 아니라, 문서와 Git 히스토리로 명확히 기록하는 것이다.

## 결정

운영 중인 개인 블로그의 메인 배포 구조는 다음 방향으로 이전한다.

- EC2 기반 상시 런타임을 제거한다.
- Nest 백엔드에 의존하던 블로그 조회 API를 빌드 산출물 기반 구조로 이전한다.
- 프런트엔드는 Vercel에서 정적으로 prerender 가능한 구조로 정리한다.
- 이전 AWS/Nest/SSM 운영 경험은 별도 문서와 Git 히스토리로 보존한다.

## 기대 효과

- 블로그 운영의 주요 고정비 제거
- 배포 파이프라인 단순화
- 운영 포인트 감소
- 도메인에 더 적합한 구조 확보
- 현재 서비스 목적과 구현 구조의 정렬

## 트레이드오프

- 서버를 직접 운영하며 얻던 인프라 경험은 운영 경로에서 줄어든다.
- 동적 API를 직접 제공하던 구조는 정적 데이터 생성 파이프라인으로 대체된다.
- 새 글 반영은 서버 런타임 반영보다 "빌드 후 재배포"에 더 의존하게 된다.

하지만 현재 블로그의 도메인과 비용 구조를 고려하면, 이 트레이드오프는 충분히 수용 가능하다.

## 보존 원칙

이전 과정에서 과거 구조를 무조건 삭제하지는 않는다. 다만 다음 원칙을 따른다.

- 현재 운영 경로에 사용되지 않는 레거시 코드는 메인 브랜치에 장기간 방치하지 않는다.
- 과거의 EC2/Nest/SSM 운영 구조는 문서, 태그, 브랜치로 보존한다.
- README에서는 전체 진화 과정을 짧게 요약하고, 상세 판단 근거는 ADR 문서로 연결한다.

이 원칙을 통해 학습과 운영의 흔적은 남기되, 현재 구조의 명확성과 유지보수성을 해치지 않도록 한다.
