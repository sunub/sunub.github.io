# Vercel Static Migration Plan

- Status: Draft
- Date: 2026-03-24

## 목적

현재 블로그는 학습과 포트폴리오 목적에서 `Next.js + Nest + EC2 + AWS SSM` 기반 운영 구조를 경험하기 위해 설계되었다. 이 경험 자체는 충분히 가치가 있지만, 실제 운영 중인 개인 블로그의 성격과 비용 구조를 고려하면 메인 운영 경로는 더 단순한 구조가 적합하다.

이 문서는 블로그를 `Vercel 기반 정적 prerender 중심 구조`로 이전하기 위한 실제 실행 계획을 정리한다.

관련 배경과 의사결정 근거는 다음 문서를 참고한다.

- [ADR-0001: 개인 블로그 운영 구조를 EC2 런타임에서 Vercel 기반 정적 배포로 이전한다](../adr/0001-migrate-from-ec2-runtime-to-vercel-static.md)

## 목표 상태

이전 후의 목표 구조는 다음과 같다.

- 운영 배포 경로는 Vercel을 기준으로 한다.
- 주요 페이지는 빌드 시점에 prerender 된다.
- 블로그 조회를 위해 Nest 런타임 서버를 상시 운영하지 않는다.
- `posts/` 기반 콘텐츠는 빌드 과정에서 정적 산출물로 변환된다.
- 검색, 아카이브, 최신 글 목록은 런타임 API 대신 정적 JSON 산출물 기반으로 동작한다.
- 과거 EC2/Nest/SSM 운영 경험은 문서와 Git 히스토리로 보존한다.

## 비목표

이번 이전의 비목표는 다음과 같다.

- 백엔드/Nest 경험 자체를 부정하거나 삭제하는 것
- 포트폴리오에서 AWS 운영 경험을 숨기는 것
- 블로그 도메인을 완전히 다른 서비스로 바꾸는 것
- 관리자 기능, DB, 인증 기능을 이번 이전 범위에 포함하는 것

## 이전 원칙

### 1. 메인 운영 경로는 단순하게 유지한다

현재 운영 중인 서비스에 사용되지 않는 경로는 메인 브랜치에서 오래 유지하지 않는다. 필요 없는 런타임 의존성을 남겨 두면 프로젝트의 현재 상태를 오해하게 만들 수 있다.

### 2. 과거 구조는 반드시 보존한다

이전 과정에서 과거의 AWS/Nest/SSM 운영 경험이 사라져서는 안 된다. 다음 중 한 가지 이상으로 흔적을 남긴다.

- Git tag
- legacy branch
- architecture 문서
- README의 요약 링크

### 3. 기능을 먼저 정적으로 바꾸고, 인프라는 나중에 정리한다

배포 타깃을 바꾸기 전에, 애플리케이션이 실제로 정적으로 동작할 수 있도록 데이터 흐름을 먼저 정리해야 한다.

### 4. 한 번에 모든 것을 지우지 않는다

정적 전환은 단계적으로 진행한다.

- 먼저 런타임 API 의존성을 제거한다.
- 그 다음 빌드 산출물 기반 구조를 안정화한다.
- 마지막에 EC2 및 관련 배포 경로를 제거한다.

## 현재 구조에서 정적 전환을 막는 핵심 요소

### 1. 요청 시점 테마 판별

현재 레이아웃은 `cookies()`와 `headers()`를 통해 요청 시점의 테마를 읽는다. 이 구조는 주요 라우트를 동적으로 분류하게 만드는 핵심 원인이다.

해결 방향:

- 서버에서 테마를 읽지 않는다.
- 클라이언트 초기화 스크립트와 브라우저 저장값으로 초기 테마를 적용한다.

### 2. rewrite 기반 백엔드 API 의존

현재 프런트는 `next.config.ts`의 `rewrites()`를 통해 `/posts/*`, `/api/*` 요청을 백엔드로 전달한다.

해결 방향:

- rewrites 제거
- 아카이브/검색/최신 글 추가 로드를 정적 데이터 기반으로 치환

### 3. 일부 페이지의 런타임 데이터 조회

아카이브, 최신 글 추가 로드, 검색은 현재 런타임 API 요청으로 동작한다.

해결 방향:

- 빌드 시 `post-index.json`, `search-index.json` 생성
- 런타임 API 대신 정적 JSON을 읽어 처리

## 단계별 실행 계획

## Phase 0. 보존 전략부터 확정

목표:

- 과거 구조의 흔적을 먼저 정리한다.

작업:

- 비용 및 이전 배경 ADR 작성
- README에 운영 구조 변화 요약 추가
- 필요 시 legacy branch 또는 tag 생성 계획 수립

완료 조건:

- "왜 이전하는가"와 "무엇을 보존할 것인가"가 문서로 명확히 남아 있다.

## Phase 1. 테마 관련 서버 의존 제거

목표:

- 주요 페이지가 정적으로 prerender 가능하도록 한다.

작업:

- `app/layout.tsx`, `(site)/layout.tsx`에서 요청 기반 테마 판별 제거
- `getRequestTheme()` 사용 제거
- 클라이언트 초기화 스크립트와 `ThemeProvider`가 초기 테마를 담당하도록 정리

예상 효과:

- 홈, 카테고리, 상세, 아카이브의 동적 판정 원인 제거

완료 조건:

- 빌드 결과에서 주요 페이지가 동적이 아닌 정적으로 분류될 수 있는 상태가 된다.

## Phase 2. 빌드 시 정적 데이터 생성 파이프라인 추가

목표:

- 블로그용 조회 데이터를 빌드 산출물로 만든다.

생성 대상:

- `frontend/public/data/post-index.json`
- `frontend/public/data/search-index.json`

`post-index.json` 포함 항목:

- 정렬된 frontmatter 목록
- category counts
- archive summary

`search-index.json` 포함 항목:

- `postKey`
- frontmatter
- headings
- searchable body text

작업:

- `frontend/scripts/generate-static-blog-data.mjs` 추가
- 기존 `posts/` 처리 로직과 검색 추출 로직 재사용 구조 정리
- `frontend` build 전에 데이터 생성 실행

완료 조건:

- 백엔드 없이도 블로그 목록, 아카이브, 검색에 필요한 데이터가 모두 정적 파일로 생성된다.

## Phase 3. 프런트의 런타임 API 제거

목표:

- 블로그 조회에 Nest API가 필요 없는 상태로 만든다.

작업:

- archive summary/range를 정적 JSON 기반으로 변경
- latest range load more를 정적 JSON 기반으로 변경
- 검색을 클라이언트 검색으로 변경
- 필요 시 검색 인덱스를 lazy load

완료 조건:

- `/posts/*`, `/api/search` 요청 없이도 사용자 기능이 유지된다.

## Phase 4. Next 설정 정리

목표:

- Vercel에서 정적으로 prerender 되는 구조로 정리한다.

작업:

- `next.config.ts`의 `rewrites()` 제거
- API 전제 헤더 설정 정리
- `vercel.json`의 `/api/*`, `/api/warmup` 등 사용하지 않는 항목 정리
- 필요 시 이미지 최적화 전략 검토

완료 조건:

- 프런트 설정에 더 이상 백엔드 런타임을 전제하는 항목이 남지 않는다.

## Phase 5. 상세 페이지 정적화 마무리

목표:

- 포스트 상세 페이지를 완전한 정적 경로 기준으로 다듬는다.

작업:

- `generateStaticParams()` 기반 경로만 배포하도록 정리
- `dynamicParams` 재검토
- 상세 페이지 데이터 소스를 빌드 시점 로컬 파일 기준으로 고정

완료 조건:

- 새 글은 재배포 시 반영되고, 운영 시점의 동적 경로 생성은 제거된다.

## Phase 6. 배포 경로 전환

목표:

- EC2/SSM 운영 경로를 메인 운영 흐름에서 제거한다.

작업:

- GitHub Actions의 EC2 deploy job 제거 또는 비활성화
- Vercel Git Integration 기준 배포 흐름 확정
- 배포 검증 체크리스트 작성

완료 조건:

- 운영 배포는 Vercel만으로 완료된다.

## Phase 7. 레거시 경로 정리

목표:

- 메인 브랜치의 현재 구조를 명확하게 만든다.

작업:

- 사용하지 않는 backend 의존 제거
- 필요 없는 AWS env 제거
- legacy 보존 경로 문서화

완료 조건:

- 메인 브랜치만 봐도 현재 운영 구조가 명확하다.

## 검증 체크리스트

- 홈 페이지가 정적으로 prerender 되는가
- 카테고리 페이지가 정적으로 prerender 되는가
- 포스트 상세 페이지가 정적으로 prerender 되는가
- 아카이브 필터 전환과 복원이 정상 동작하는가
- 검색이 API 없이 동작하는가
- 최신 글 추가 로드가 정상 동작하는가
- 신규 글 추가 후 재배포 시 반영되는가
- `EC2_PUBLIC_API_URL`, `BACKEND_API_URL`, rewrite 의존 없이 배포 가능한가

## 위험 요소

### 1. 테마 초기화 방식 변경에 따른 hydration 이슈

요청 시점 테마 판별을 제거하면 초기 깜빡임이나 hydration mismatch를 유발할 수 있다. 이 부분은 사전 검증이 필요하다.

### 2. 검색 품질 저하 가능성

현재 검색은 한글 검색을 위해 커스텀 매칭 로직을 사용한다. 단순한 클라이언트 필터링으로 바꾸면 품질이 떨어질 수 있으므로 기존 유틸리티를 재사용해야 한다.

### 3. 아카이브와 무한 로드 UX 변화

정적 JSON 기반으로 바꾸는 과정에서 현재의 로딩 UX나 복원 로직이 흔들릴 수 있다. 기능 동등성을 기준으로 검증해야 한다.

## 성공 기준

이번 이전은 단순히 EC2를 제거하는 것이 아니라, 다음 상태를 달성했을 때 성공으로 본다.

- 현재 블로그의 사용자 경험이 유지된다.
- 운영 비용 구조가 블로그 도메인에 맞게 단순화된다.
- 메인 브랜치가 현재 운영 구조를 명확하게 반영한다.
- 과거의 AWS/Nest/SSM 경험은 문서와 Git 히스토리로 보존된다.
