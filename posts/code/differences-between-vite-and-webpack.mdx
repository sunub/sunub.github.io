## vite vs webpack

오늘날 새로운 프로젝트를 시작한다고 할 경우 가장 빠르게 인기를 얻고 webpack에 비해서 뛰어난 성능을 갖고 있으며 다양한 프레임워크를 지원해주는 vite 을 사용하지 않아야 하는 이유가 있나? 어떠한 차이가 있어서 그런 것일까? 에 대한 궁금증이 있었기 때문에 저희는 vite와 webpack의 차이점에 대해서 분석 해보았습니다.

`vite`가 성능이 뛰어난 이유는 무엇일까요? vite는 `esbuild`, `Rollup`, `SWC` 들의 장점들을 최대한 활용하여 등장한 번들링 툴이기 때문입니다.

### vite와 webpack이 AST를 처리하는 방법

AST는 코드 텍스트에서 트리 구조의 데이터 스트럭쳐를 만들어 낸다.

```js
function square(n) {
  return n * n;
}
```

위의 코드를

```js
{
	"type": "Program",
	"start": 0,
	"end": 36,
	"loc": {
		"start": {
			"line": 1,
			"column": 0
		},
		"end": {
			"line": 3,
			"column": 1
		}
	},
	"range": [0, 36],
	"errors": [],
	"comments": [],
	...
}
```

위와 같은 트리 구조의 데이터 스트럭쳐를 만들어내는 것을 AST processing 이라고 하며 현대에서 사용하고 있는 많은 컴파일러들 `babel`, `esbuild` 등에서 이루어지고 있는 작업입니다.

그렇다면 지금까지 AST를 설명한 이유는 무엇일까요? Webpack와 Vite의 AST 처리 방식 차이는 빌드 성능에 영향을 미치기 때문입니다.

### Webpack의 처리 방법

```text
// Webpack의 AST 처리
코드 → JavaScript AST 생성 → 변환 → JavaScript 코드 생성
```

Webpack은 모든 모듈을 정적으로 분석하고, AST를 생성하여 의존성 그래프를 구성합니다. 전체 애플리케이션 코드가 AST 형태로 변환되어 번들링 과정이 이루어지며, HMR 시에도 관련된 모듈만 다시 AST를 생성해 업데이트합니다. 이 과정은 의존성이 복잡한 대규모 프로젝트에서 번들링 시간이 길어지는 원인이 되기도 합니다.

> HMR 이란?
> `Hot Module Replacement` 의 약자로 모듈 전체를 다시 로드하지 않고 애플리케이션이 실행되는 동안 변경 사항에 대해서 교환, 추가 또는 제거 방법을 통해서 변경 사항만을 갱신하고 개발 시간을 절약하는 방법입니다.

webpack에서 HMR을 처리하는 방법은 아래와 같습니다

```text
변경 감지 및 컴파일

파일 변경 감지
↓
전체 모듈 그래프 재구성
↓
변경된 모듈과 의존성 있는 모듈 다시 컴파일
↓
HMR Runtime에 업데이트 알림
↓
브라우저에서 새 모듈로 교체
```

webpack은 변경사항이 발생 되었을 경우 해당 모듈에서 변경된 부분만을 교체하는 것이 아니라 변경사항이 발생한 모듈 자체를 새롭게 AST를 생성하고 해당 모듈 전체를 교체하는 과정을 갖는 다는 특징을 갖고 있습니다.

### Vite의 처리 방법

```text
 Vite(esbuild)의 AST 처리

코드 → 바이너리 AST 생성 → 변환 → JavaScript 코드 생성
```

반면에 Vite은 esbuild를 활용하여 AST를 처리하고 esbuild는 필요한 모듈만 개별적으로 파싱하여 AST를 생성합니다. 그리고 ESM을 활용하여 브라우저의 모듈 로딩을 그대로 사용하고 코드에서 변경 사항이 생겼을 경우, HMR 시 변경된 모듈만을 처리하여 빌드를 진행합니다.

```text
 변경 감지 및 처리

파일 변경 감지
↓
변경된 모듈만 ESM으로 처리
↓
브라우저에 변경 알림
↓
브라우저가 변경된 모듈만 다시 요청
```

위에서 설명한 내용을 토대로 알 수 있듯이 webpack와 vite이 빌드 시 AST를 처리하는 방식에는 효율성의 차이가 있다는 것을 알 수 있습니다.

오늘날 새로운 프로젝트를 시작한다고 할 경우 가장 빠르게 인기를 얻고 webpack에 비해서 뛰어난 성능을 갖고 있으며 다양한 프레임워크를 지원해주는 vite 을 사용하지 않아야 하는 이유가 있나? 어떠한 차이가 있어서 그런 것일까? 에 대한 궁금증이 있었기 때문에 저희는 vite와 webpack의 차이점에 대해서 분석 해보았습니다.

webpack은 변경 사항이 발생 되었을 경우 해당 모듈에서 `의존(dependencies)` 되어 있는 모든 모듈들을 불러오고 변경된 모듈 뿐만 아니라 모듈에 의존 되어 있는 모든 모듈들을 새롭게 AST를 생성하고 해당 모듈 전체를 교체하는 과정을 갖는 다는 특징을 갖고 있습니다.

#### Vite의 처리 방법

```text
 Vite(esbuild)의 AST 처리

코드 → 바이너리 AST 생성 → 변환 → JavaScript 코드 생성
```

반면에 Vite은 개발 서버에서는 esbuild를 활용하여 AST를 처리하고 Production 환경에서 번들링을 진행할 경우에는 Rollup을 사용하여 번들링을 진행합니다. esbuild의 경우 필요한 모듈만 개별적으로 파싱하여 AST를 생성합니다. 그리고 ESM을 활용하여 브라우저의 모듈 로딩을 그대로 사용하고 코드에서 변경 사항이 생겼을 경우, HMR 시 변경된 모듈 만을 처리하여 빌드를 진행합니다.

```text
 변경 감지 및 처리

파일 변경 감지
↓
변경된 모듈만 ESM으로 처리
↓
브라우저에 변경 알림
↓
브라우저가 변경된 모듈만 다시 요청
```

vite은 ESM을 사용하고 ESM을 활용하면 브라우저가 필요한 모듈만 즉시 불러와서 실행할 수 있습니다. 특정 컴포넌트를 수정할 때 해당 컴포넌트 파일만 다시 로드하면 되므로, 전체 애플리케이션을 다시 번들링하는 과정이 필요 없어집니다.

또한 ESM을 사용할 경우 필요할 때마다 개별 모듈을 로드하여 처리하기 때문에, Webpack처럼 모든 모듈의 AST를 한꺼번에 메모리에 로드하지 않습니다. 그렇기 때문에 ESM을 활용하는 Vite이 Webpack보다 낮은 메모리 사용량으로 개발 서버를 구동할 수 있습니다.

### 결론

저희는 단적으로 번들링 과정에서의 webpack과 vite 의 성능 차이에서 다루어 보았습니다. 위의 글에서 알 수 있듯이 ESM을 활용하여 번들링을 진행하는 vite이 성능 상 webpack 보다 뛰어나기 때문에 저희는 vite을 선택하기로 결정했습니다. 하지만 번들링 이외에도 vite은 webpack보다 뛰어난 장점을 많이 갖고 있고 React를 사용하여 프로젝트를 진행하기에 적합한 번들러 도구이기 때문에 저희는 `vite`가 webpack에 비해 뛰어난 성능을 갖고 있으며 다양한 프레임워크를 지원해주는 번들러 도구라는 결론을 내렸습니다.
